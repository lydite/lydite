# A secret is found by gitleaks, once over the working tree, and the claim it makes is *rotate*

Nothing in `lydite scan` looks for a committed credential. gosec's `G101` fires on
credential-shaped patterns in Go source and nowhere else, so a key in a `.env`, a workflow, a
TypeScript module or a fixture reaches the default branch with every row green — under a tool
that describes itself as the single entry point for security scanning. This closes
[#20](https://github.com/lydite/lydite/issues/20).

**`lydite scan` runs a pinned gitleaks once over the scan root's working tree. Its claims name no
component and their count is recorded in `root_findings`, beside Semgrep's. The gate never quotes
the secret — not in the terminal, not in `scan.json` and not in a `site` — and every message it
writes says to rotate the credential, because deleting one does not undo the leak. A false
positive is answered in gitleaks' own configuration, and `.lydite/config.yml` gains one key:
`secrets.enabled`.**

## gitleaks, installed the way gosec is

`gitleaks dir` is a single static Go binary with no runtime, a maintained default ruleset, an
inline allow syntax and a JSON report written *beside* its terminal output rather than instead of
it. That last property is what [ADR 0032](0032-every-scanner-reports-its-findings-as-data.md)
asks of every scanner, and gitleaks satisfies it in one pass:

```
gitleaks dir --no-banner --redact --verbose --report-format json --report-path <tmpfile> .
```

run with the scan root as the working directory. Exit 1 is leaks found and exit 0 is clean, but
the report carries no error array and no summary, so gitleaks exits 1 for a directory it could
not walk exactly as it does for a leak it found. **The row follows the claims that survive
scoping**, not that status; the status is read against the report to answer a different question,
which is whether gitleaks walked at all. An unreadable report, an exit the report does not
account for, a leak that names no line inside the scan root, and a scope git could not be asked
for each fail the row with its reason in `Detail`. The amendment below states the scoping this
verdict follows, and the limits of the four.

Three flags are load-bearing and none is a preference. `--verbose` is what makes gitleaks print
its findings at all; without it the run prints `leaks found: 61` and the author is told a count
and no location. `--redact` replaces the matched text with `REDACTED` in **both** the terminal
output and the JSON report, so a CI log and a report artifact of a failing run carry no
credential. `--report-path` writes a copy, so the human stream and the exit status are untouched
and the check needs no second pass.

**The pin is a module of its own**, `internal/secrets/gitleaks-pin/go.mod`, with a Go constant in
`internal/secrets/pins.go` mirrored by `internal/pins` — the arrangement `internal/golang/go-pin`
already has, for the reason [tool-pins.md](../../agentic/references/tool-pins.md) gives: `go:embed`
cannot read across a module boundary, and gitleaks' dependency graph in lydite's own `go.mod`
would be a stream of Dependabot pull requests about code lydite never links. It gets a `gomod`
entry in `.gt-repo.yaml`, and the `*-pin` name puts it inside the exclude glob
`source/cli/internal/**/*-pin/**` already in `.lydite/components.yml`.

Two facts that cost an afternoon to find, recorded rather than rediscovered. The module path is
`github.com/zricethezav/gitleaks/v8`; the repository moved to `gitleaks/gitleaks` and the module
path did not, so requiring the new one fails resolution with *module declares its path as*. And a
`go install`ed gitleaks is built without the release ldflags, so `gitleaks version` prints
`version is set by build process` — the "is the pinned version already installed" probe
`internal/semgrep` does is impossible here, and the version-keyed bin directory `internal/gotool`
creates is the whole of the guarantee, exactly as it is for gosec. The install is keyed by that
version alone and not by a component's Go toolchain, because gitleaks analyses no Go source — the
same distinction that makes gotestsum's pin a module of its own. It installs with lydite's own
environment and never a component's, because a check and an install do not share one.

**Rejected: TruffleHog.** Its distinguishing feature is live verification, which sends candidate
credentials to third-party APIs from whatever machine the scan runs on and makes the verdict
depend on network reachability. `lydite scan` has to give the same answer locally and in CI, and
a gate that phones a vendor from a developer's laptop is one no repository can adopt without a
policy conversation. With `--no-verification` it is a regex scanner with a noisier ruleset and no
inline allow comment, which is strictly the worse half of this decision.

**Rejected: detect-secrets.** Its opt-out model is a `.secrets.baseline` file of hashed,
line-keyed entries regenerated by a tool and audited out of band. Line-keyed identity is what
[findings.md](../../agentic/references/findings.md) rejects — an edit above a secret invalidates the
entry — and a whole-repository suppression file is the channel `.lydite/config.yml` deliberately
does not have.

**Rejected: Semgrep's secrets rules.** They are the Platform product, not the community ruleset
lydite runs, so the gate's coverage would depend on whether a run happened to carry a
`SEMGREP_APP_TOKEN`. Whether a pull request is green is not allowed to be a property of which
secrets the job had — `semgrepBase` exists because of exactly that.

**Rejected: importing gitleaks as a library.** ADR 0032's whole stance is that the tool keeps
printing its own findings, and linking it would put its dependency graph in the binary that
`go-pin` exists to keep it out of.

**Rejected: a release binary through `internal/download`.** That is how language toolchains
arrive, and it means per-platform checksums maintained by hand against a manifest Dependabot
cannot read. A pin nothing ages out is the failure the pin arrangement exists to prevent.

## Root-scoped, because a secret is not a language

Semgrep is root-scoped and this is the second gate that is. A secret scanner reads bytes, not a
build graph: it has no language to be per-language about, and the files most likely to carry a
credential — `.github/workflows/`, a `docker-compose.yml`, an `.env` somebody committed — belong
to no component at all. Its claims therefore carry no `Finding.Component`, which is what an empty
one already means, and `findingCounts` puts the count in `ledger.Record.RootFindings` beside the
components rather than inside one. Nothing may attribute a claim to whichever component happens
to contain its path; that is the ownership question
[ADR 0033](0033-a-finding-count-per-gate-reaches-the-ledger.md) refuses to invent an answer to.

**Rejected: per component, through `scannerGates`.** It would mean listing the gate under Go,
Rust and TypeScript alike — three declarations of one file-shaped fact — while leaving every path
outside a component unscanned, and scanning a file claimed by two components twice.

The cost [ADR 0020](0020-scan-on-components.md) already accepted for Semgrep is inherited
unchanged and is worth restating, because it is sharper here: a repository that declares no
components is an error before either root-scoped gate runs, so a repository with nothing declared
gets no secret scan.

The gate is **not** diff-scoped. gitleaks' `--baseline-path` takes a previous report rather than a
commit, so there is no equivalent of Semgrep's `--baseline-commit`, and inventing one would mean
lydite deciding which of its own findings are new. So the row fails on every secret in the tree,
as gosec's does; the anchor decides which claims become threads on the change and which land in
the standing comment as the pre-existing debt they are.

## The working tree, not the history

`gitleaks git` scans every blob in every reachable commit. It is the more thorough question and
the answer is no.

Three reasons, in order of weight. The count recorded in `root_findings` has to be a property of
the tree being recorded, like every other scalar the ledger holds; a history count is
monotonic-by-construction, never falls when a secret is fixed, and would draw a rising line that
no commit can ever bend. A claim about a blob that exists in no working file has no line to
anchor to and no edit that clears it, so it is not a finding under this repository's own
definition — it is an incident. And history mode needs `fetch-depth: 0` in every consumer's
checkout, undoing precisely what ADR 0033 arranged when it made the baseline scan the one lydite
job that needs no full clone.

**What this gives up, stated rather than buried:** a credential committed and later deleted stays
leaked and lydite will never mention it. Also a pull request that adds a secret in one commit and
removes it in the next merges green while having published the secret.

**Rejected: scanning `<merge-base>..HEAD` as a second pass.** It closes the second case and costs
the full clone the first reason rejects, plus a dedup rule between two passes' claims and a second
verdict to fold into one row. A history sweep is an audit somebody runs once, not a per-pull-request
gate, and it belongs to whatever answers the incident rather than to `scan`.

## The claim is *rotate*, and it never quotes the secret

`Finding.Message` is the only text the author of a pull request reads, and gitleaks' own
description ends at what it found: *"Detected a Generic API Key, potentially exposing access to
various services and sensitive operations."* An author who reads that deletes the line, pushes,
watches the row go green and has fixed nothing — the credential is in a pushed commit and stays
valid until somebody revokes it. So every message carries one appended sentence, verbatim:

> Rotate this credential: deleting it does not undo the leak, because the commit that carries it
> is already pushed.

The message is the rule's description with its trailing full stop normalised, then that sentence.
A rule with no description reads `gitleaks matched <rule id>.` followed by the same sentence.

**Rejected: putting the instruction in `Finding.Detail`.** A located claim becomes a review thread
showing the message, and the reader who most needs the instruction is the one who sees only that
line.

**`Finding.Detail` is empty.** Everything gitleaks would put there is either already a field —
the rule, the description — or is the secret.

### The site is the line with the match cut out of it

This is a departure from [findings.md](../../agentic/references/findings.md), where a scanner's site
is the rule with the source text it fired on, read from the tree. Here that source text *is the
credential*, and `site` travels in `scan.json` and into the standing comment on a public pull
request. A gate that publishes the secret it found in order to identify it stably is worse than
no gate.

So the site is the rule id, then the start line's text **up to** the match's start column, read
from the tree through `finding.Source` and never from the report — which carries `REDACTED` under
`--redact` anyway. In practice that is the assignment context, `apiKey: `, which is exactly the
part that survives an edit above it and tells two secrets in one file apart. The column is clamped
to the line's length and to a rune boundary; a match starting at column 1 yields a site of the rule
alone, and `ordinal` separates those in source order as it does everywhere else.

The cost is accepted and named: two secrets under one rule with no distinguishing prefix in one
file are ordinals 0 and 1, so rotating the first re-identifies the second and its thread is
posted afresh. That is the fingerprint behaving as specified on a claim whose only honest
distinguishing content may not be published.

Cutting at the match's own start column protects a claim from its own secret and from a second
flagged match sharing the line, but not from a credential gitleaks' own rules never fired on —
`export DB_PASSWORD=hunter2 API_TOKEN=<token>`, a JSON `{"password": "hunter2!", "api_key": …}`,
a DSN's password ahead of an `api_key` parameter, `mysql -u root -phunter2 --api-key=<token>`.
None of those needs a colon, an equals sign or a quote — a command-line flag is letters, digits
and a leading dash — so a blocklist of dangerous characters keeps discovering a new shape it
forgot to name. The prefix is instead an allowlist of one shape: it survives only when it is,
in full, a single identifier optionally followed by one opening bracket — `connect(`, `clé` —
checked after clipping so a clipped-away tail cannot cause an already-safe head to be discarded
too. Anything with a second word, a digit-and-punctuation flag, a colon or a quote in it is not
provably safe, so it is not published; the site is the rule alone instead.

**Rejected: gitleaks' own `Fingerprint`.** It is `file:rule:startline`, a line-keyed identity —
the one thing `internal/finding` exists to not be.

**Rejected: a hash of the secret.** It is stable and it publishes an offline-crackable digest of
a live credential for every low-entropy match, in a document lydite uploads.

## A false positive is answered in gitleaks' own configuration

This gate fires on fixtures more than any other, and that is not hypothetical: over this
repository's own tree it reports 61 findings, of which 60 are one rule against one captured
`govulncheck` report whose googlesource URLs carry 40-hex commit hashes.

Three properties settle how that is answered, and none of them is a new lydite surface.

**`.lydite/config.yml` gains `secrets.enabled` and nothing else.** It opts out of the whole gate,
which is all that file does — tuning severity and suppressing individual findings is explicitly
not its job (see [configuration.md](../../agentic/references/configuration.md)). Switched off, the
gate runs nothing, reports no row and records no count, exactly as a disabled language does.
The section is named for the concern and the **gate is named for the tool**, `gitleaks`, as
`gosec` and `semgrep` are: a row names what a reader would re-run, while a repository declining
this is declining secret scanning rather than a vendor.

**lydite passes no `--config`.** gitleaks discovers `.gitleaks.toml` at the scan root itself, so a
repository states its allowlist in the tool's own configuration, where the rest of its scanning
policy already lives. This is deliberately Semgrep's arrangement and not Biome's: lydite passes
Biome a `--config-path` that beats the scanned project's own file, which ADR 0020 records as a
real limitation rather than a model to copy. lydite's own tree needs one such file, and the shape
is worth recording because it takes the count from 61 to 1:

```toml
[extend]
useDefault = true

[[allowlists]]
description = "captured govulncheck report: googlesource commit hashes read as access tokens"
targetRules = ["sourcegraph-access-token"]
paths = ['''source/cli/internal/golang/testdata/govulncheck\.json''']
```

**Rejected: excluding `testdata/` wholesale.** gosec already scans `testdata/`, which the go tool
itself skips, and for the right reason — a fixture is committed code and a credential in one is a
credential in the repository. A path-shaped blanket exclude would also make the one place a real
key is most likely to be pasted the one place nothing looks.

**Rejected: `.gitleaksignore` and `--baseline-path`.** Both are fingerprint lists keyed by
`file:rule:line`, so they lapse silently the moment anything above the secret is edited, and
neither says why the entry is there. A `[[allowlists]]` block carries a `description` and a rule
id, and a diff of one is reviewable.

**Inline, the syntax is gitleaks' own: `gitleaks:allow` on the line.** `--ignore-gitleaks-allow`
is deliberately not passed. Adding one is a net-new suppression annotation and therefore a
referral — which requires `gitleaks:allow` in `internal/referral`'s `suppressionMarkers`, without
which the one opt-out this gate expects to see used most is the one that merges unattended.

**Named and accepted: `.gitleaks.toml`'s own `[extend].path` is not a disqualifier.** gitleaks
lets one config file extend another, and an edit to the extended file can widen an allowlist just
as an edit to `.gitleaks.toml` itself can — but resolving `[extend].path` at referral time means
parsing TOML and following a path lydite does not otherwise read, for a feature this repository's
own `.gitleaks.toml` does not use. A repository that does extend its config is expected to name
the extended file in its own `extra.Paths` disqualifiers (`.lydite/exemptions.yml`) until this
gate's disqualifier resolves the reference itself.

## Consequences

- `lydite scan` grows one row, `gitleaks`, unlabelled by component, and `scan.json` grows its
  claims under the existing `findings` key. `findingCounts` needs no new concept: a root-scoped
  gate already lands in `root_findings`, and a test says so for this gate too.
- A repository adopting lydite meets its own standing secret debt on the first pull request, red,
  as it already does for gosec. The located claims reach the diff and the rest are listed in the
  standing comment as debt.
- The whole of the working tree is read on every scan — 5.1 MB of this repository in 1.6s — and
  nothing about that scales with history, which is the point of the previous section.
- A credential deleted before lydite was adopted stays leaked and unmentioned. That is an audit
  somebody runs with `gitleaks git`, and it is not this gate.
- One more report shape is lydite's to track. It is parsed from a captured real report, and an
  unrecognised field is reported rather than dropped — a capture that itself trips the scanner is
  committed with a `.txt` suffix and loaded through `internal/fixture`, as this repository's other
  probe fixtures already are.
- `internal/referral` must learn `gitleaks:allow`. Until it does, the suppression this gate is
  most likely to attract is the only one that clears a finding without a human.

## Amendment (2026-09-20): a path `.gitignore` covers is not part of the working tree this gate reports on

The scan is still root-scoped, still one pass over the working tree, and still not over history.
What this amends is which files that working tree is taken to hold: a path `.gitignore` covers is
not one of them for this gate's purposes, so a leak in it produces no claim.

The title above packs two axes — whole-repo versus per-component, and current files versus git
history — and this is a third, which is why nothing above rejects it: it was never raised, over a
tree that carries no build output. A tree that carries some reads very differently. A warm Rust
`target/` holds compiled-in test vectors that gitleaks' `private-key` and `generic-api-key` rules
fire on by the dozen — 27 of them in one pilot, nearly all in
`target/llvm-cov-target/debug/deps/*.rmeta` — and every one sits in a file git will not carry.

### `[[allowlists]]` is the right instrument for a fixture and the wrong one for build output

The section above settles how a false positive is answered — a `[[allowlists]]` block in the
repository's own `.gitleaks.toml`, which lydite reaches by passing no `--config` — and that stays
exactly as it is for a credential-shaped string in a committed fixture. Build output is not that.
It is not a false positive in a file under review; it is a compiler cache, and answering it
through the config would have every adopting repository enumerate the artefacts of its own
toolchain to get a clean scan. A blanket `target/` path allowlist in every consumer's
`.gitleaks.toml` is an adoption tax paid for lydite's failure to ask git a question git already
answers. `.gitleaksignore` and `--baseline-path` remain rejected for the reason stated above, and
that reason is sharper here: a fingerprint list keyed by `file:rule:line` over a regenerated
`target/` lapses on every rebuild.

**Rejected: generating a config to inject path allowlists.** It means passing `--config`, which
takes the repository's own `.gitleaks.toml` away — the arrangement this ADR chose deliberately —
and `[extend]`-merging it back is a translation problem, because `.gitignore` patterns are not
regexes. It buys nothing the scoping below does not.

### The walk cannot be scoped, so the claims are

`gitleaks dir` (v8.30.1, `cmd/directory.go`) accepts exactly one path, and none of its global
flags controls which paths are walked: there is no `.gitignore` integration, no exclude flag and
no way to hand it a file list. Its only exclusion mechanisms are the three already named here —
`.gitleaksignore` fingerprints, config allowlists, and inline `gitleaks:allow`.

So the filter sits between the report and the findings. `gitdiff.Tracked` runs
`git ls-files -z --cached --others --exclude-standard` and returns exactly the set this gate has a
claim over: what git tracks, plus what is untracked and not ignored, minus everything
`.gitignore` covers. Its paths are relative to the scan root and slash-separated, which is the
shape a `Finding.Path` already carries, so the two compare as text.

**The precedent is lydite's own, and it is not Semgrep.** `internal/mutation/worktree.go` calls
`gitdiff.Tracked` to decide what to copy into a mutation worker, precisely so `target/`,
`node_modules/`, `dist/` and `.git` stay out without lydite re-deriving a judgement `.gitignore`
already states, and `internal/orphan` calls it for the same reason — keeping files that are
untracked and not ignored in scope deliberately, since a newly authored, not-yet-added source
file is the moment its author can most cheaply fix a finding. Semgrep's tracked-file behaviour is
semgrep's own default and lydite passes nothing to request it, so there is no lydite code there
to copy.

**This is deliberately not a suppression.** `internal/referral`'s `suppressionMarkers` treats
`gitleaks:allow` as one, and a suppression is a thing that *refers* — which is correct for an
author writing a marker beside a finding and wrong for this. A gitignored path is not a
suppressed finding; it is a file this gate has no claim over. Implemented as a suppression, every
repository with a `target/` would be permanently referred, which is a worse failure than the one
being fixed.

### What it gives up, and why that is the right trade

A real credential sitting in a gitignored file is not reported at all. That is the whole of the
cost and it is stated rather than buried.

The trade is right because the gate's claim is *rotate this credential* and its scope is what the
repository could publish. A file git will not carry cannot be committed by accident — it takes a
deliberate `git add -f` — so the leak this gate exists to catch is not reachable from there. An
untracked file that is *not* ignored is one `git add .` from being published, and
`--others --exclude-standard` keeps exactly those in scope. A developer's `.env` holding live
credentials is the common shape of what is given up, and it is a shape that was never one commit
from the default branch.

### The verdict follows the claims, and a gate that could not run says so

Scoping the claims makes the exit status unusable as the verdict: gitleaks exits 1 because it
found something in `target/`, and a gate whose every claim was filtered away must not still fail.
So the row follows the claims that survive, and what the status is still read for is whether
gitleaks walked at all — a run that did not is the one thing an empty claim list cannot otherwise
be told apart from a clean tree.

Four outcomes are this gate failing rather than this gate's finding, and each fails the row with
its reason in `Detail`: a report lydite could not read, an exit the report does not account for,
a leak that could not be placed inside the scan root, and a scope git could not be asked for. The
last of those reports every claim unscoped as well as failing: a scope lydite could not establish
costs the row, never the claims, because a pass there is indistinguishable from a tree that was
scoped and clean.

Three limits of that are named rather than claimed away.

- **A failing row is the strictest thing available here, not the precise one.** The grammar's own
  status for a gate that could not run is the amber `StatusUnmeasured`
  ([output-grammar.md](../../agentic/references/output-grammar.md)), and `executil.Result` carries
  a verdict as an error or nothing, so `resultRows` has only pass and fail to render these as.
  Red overstating a gate that could not run is the direction
  [`a-gate-that-could-not-run-never-renders-as-one-that-passed`](../../agentic/rules/a-gate-that-could-not-run-never-renders-as-one-that-passed.md)
  asks for; a third status here is a change to `executil.Result`'s shape and to every caller of it.
- **A partial walk that exits 1 with a non-empty report is indistinguishable from a finished
  one.** gitleaks writes nothing that separates them. What it costs is a run whose surviving
  claims were all filtered away passing on a walk that stopped early.
- **`lydite scan --dir <a gitignored subtree>` reports clean.** `git ls-files` run inside an
  ignored directory lists nothing, so every claim is filtered and the gate finds no leak in a
  tree it may well have leaks in. The scan root is meant to be the repository root, where this
  cannot arise; a root inside an ignored subtree is not detected as the degenerate case it is.

### Known cost: the whole tree is still walked

gitleaks reads every file under the scan root, ignored or not, so a repository with a
multi-gigabyte `target/` pays the full walk for a report most of which is then filtered away.
Scoping the claims buys correctness and no speed at all. A shadow tree of tracked files built to
hand gitleaks a smaller walk is rejected: it is a second copy of the repository per scan, and the
paths in the report would then name the copy rather than the tree a site is read from.
