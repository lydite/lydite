# v0.4.0 — pnpm runs as its own native binary, and an unsupported pin is refused

Every component whose workspace pinned pnpm 12 or later failed its install unconditionally:
pnpm's own registry package ships a placeholder at `bin/pnpm` from that major on, meant to be
overwritten by a `preinstall` lifecycle script lydite does not run. pnpm is now provisioned as
its native `@pnpm/exe.<os>-<arch>` binary directly — fetched and verified along a chain rooted
in the pnpm tarball's own registry digest, with no lifecycle script and no wrapper — so a pnpm
12+ pin now installs and runs correctly.

## Breaking: a `packageManager` pin below pnpm 12 now fails that component's install

pnpm's registry package only takes the native-binary shape this release provisions against from
major 12 on. A workspace pinning pnpm below 12 in `packageManager` now fails at install time,
naming the manifest and the pin, rather than silently running whatever pnpm happened to be on
PATH. Every other component in the run is unaffected.

**If your `packageManager` field pins pnpm below major 12**, either:

- bump the pin to pnpm ≥ 12, or
- set `toolchain.enabled: false` in `.lydite/config.yml` to let the install run whatever pnpm
  is already on the runner.

## `lydite mutation` keeps what it measured, and can stop at a deadline

A mutation run that died at a CI job timeout used to keep nothing, so a change large enough to
outrun the job outran it on every retry. Two additions change that. Neither alters a run that
passes neither flag, except that state is now kept.

**Resume.** Every mutant verdict is recorded as it lands, under a state directory (`--state-dir`,
or `$LYDITE_MUTATION_STATE`; a cache directory keyed by the scan root by default). A rerun over
an identical tree, runner, toolchain, limits and environment reuses the recorded baseline and
every recorded verdict and measures only what is left. The report says how many verdicts were
reused. Any other fingerprint discards the state, and `--fresh` discards it on demand. The state
is a cache: a failure to read or write it is a diagnostic, never a failed run.

**Deadline.** `--deadline <duration>`, measured from process start, stops dispatching mutants,
cancels those in flight and keeps every verdict already reached. The component is reported as
`unmeasured` — "N of M measured, rerun to resume" — or as a failure if a survivor was already
found. There is no deadline unless you pass one.

**What a consumer sees.**

- An incomplete run exits **3**, including under `--no-gate`, because an `unmeasured` row does not
  vote. A survivor still wins and exits 1. A pipeline that treats every non-zero exit as a failure
  needs no change; one that distinguishes exit codes should treat 3 as "rerun to resume".
- The `--json` document's `verdict` field gains the value `incomplete`.
- `mutants.json` records an incomplete component under its own `incomplete_components` key, never
  under `components`, so an older reader finds it absent rather than reading a partial count as a
  finished score. `lydite mutation merge` folds an incomplete component over a complete one and
  exits 3; `lydite test record` never records a partial count.

The CI wiring that saves and restores the state between attempts ships separately in
`lydite/actions`.
