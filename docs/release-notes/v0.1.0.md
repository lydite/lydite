# v0.1.0 — bulwark is now lydite

**No functional change.** This is the same scanner that shipped as bulwark
v2.0.0, under a new name, in a new organisation, with the GitHub Action moved
to a repository of its own. Everything it checks, and every number it reports,
is unchanged.

The rename happened because `bulwark` was unavailable on GitHub — held since
2014 by an account with no repositories and no activity since 2017 — and
because the project had outgrown the organisation it was created in, having
become the quality gate for several unrelated projects rather than one.

Lydite is the black touchstone an assayer rubs gold against: the colour of the
streak reveals the metal's purity. It is, literally, an instrument for testing
quality against a standard.

## Upgrading

Five things change for a consumer. Nothing else does.

**1. The action moves to its own repository.**

```yaml
- uses: lydite/actions/scan@v1   # was wardnet/bulwark@v2
```

The inputs are identical. The action lives apart from the CLI now because
GitHub clones the whole repository backing a `uses:` on every job, and because
pinning `@v1` for the action should not churn every time the scanner releases a
patch.

**2. `.bulwark.yml` becomes `.lydite.yml`.** Same schema, same keys, same
values — only the filename changes. A repo that still has `.bulwark.yml` is a
repo lydite believes has no configuration, which means pin directories stop
being excluded and coverage source falls back to `run`.

**3. The state branch is renamed.** `bulwark-state` becomes `lydite`. Nothing
migrates it: baselines are a cache, and a cache that is cheaper to recompute
than to move should be recomputed. The practical effect is that **the first
pull request after upgrading reports every language as `[NEW]` and gates on
nothing**, exactly as a repo's very first run does. Merge it, let the main build
record baselines on the new branch, and the next pull request gates normally.
The old `bulwark-state` branch is never read again and can be deleted whenever
convenient.

**4. Environment variables are renamed.** `BULWARK_VERSION` and
`BULWARK_INSTALL_DIR` become `LYDITE_VERSION` and `LYDITE_INSTALL_DIR`.

**5. The install URL and the binary change name.**

```sh
curl -fsSL https://github.com/lydite/lydite/releases/latest/download/install.sh | sh
```

The binary is `lydite`; `lydite update` self-updates in place. Remove the old
`bulwark` binary from `~/.local/bin` at your leisure — nothing refers to it.

If you are upgrading from bulwark **v1.x** rather than v2.0.0, one further
change applies: ESLint was removed and Biome is now the only TypeScript linter,
so a config carrying `typescript.linter: eslint` will fail to load. Coverage
also became line-weighted in that release, which moves every repo's headline
number.

## Why 0.1.0 and not 3.0.0

Version continuity exists for consumers who pin a version, and after this
migration nobody does: the action is pinned at `lydite/actions/scan@v1`, and
the CLI version resolves as `latest`.

`0.x` also says something true. The next work is quality history — a ledger of
coverage, test results and finding counts kept on the state branch and rendered
as a dashboard — and that storage layout will change once there is real data in
it. Starting at `0.1.0` leaves `1.0.0` free to mean the release where the
dashboard ships.

It does understate a scanner that has been hardening across six repositories
for a long time. That is the one cost, and it expires at 1.0.0.

`lydite/actions` starts at `v1.0.0` independently: its version denotes the
action's input interface, which is stable and inherited unchanged.

## What is not affected

Every check, every pinned tool version, the coverage gate and its baselines,
the pull-request summary, and the `.lydite.yml` schema. The Go module path
changed to `lydite/lydite` but remains deliberately non-fetchable — lydite is a
binary, installed by `install.sh`, and nothing should import it.
