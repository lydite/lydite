# v0.2.0 — coverage is measured per component, by `lydite test`

`lydite coverage` is removed. `lydite test` measures every component's coverage
from the instrumented variant its runner already derives, and
`lydite test --gate-coverage` gates it against the baseline.

This is the release where the component — declared in `.lydite/components.yml`,
introduced across the previous releases — becomes the unit coverage is measured
and gated over. Coverage was the last gate still discovering its own units by
walking for manifests.

## Upgrading

**1. Replace the command.**

```sh
lydite coverage --dir .                     # before
lydite test --dir . --gate-coverage         # now
```

`lydite test` measures coverage on every run; `--gate-coverage` is what reads
the baseline, compares against it and records a new one. The flag is explicit
because measuring is local and gating pushes to a shared branch — a developer's
`lydite test` must never write to it. `--no-coverage` runs each component's
plain variant and reports no coverage at all.

Running `lydite coverage` now fails with a message naming its replacement
rather than "unknown command".

**2. Remove these keys from `.lydite/config.yml`.** Each is now **rejected**,
not ignored — a silently dropped key is a repository measuring something other
than what its author wrote while every run still reports a pass.

| Removed | Why |
|---|---|
| `coverage.source` | lydite measures from each component's own instrumented run, so no pipeline half owns producing coverage |
| `coverage.go.report` | lydite writes every report itself, at a path derived from the component's runner |
| `coverage.rust.report` | as above |
| `coverage.rust.lcov` | as above |

The matching flags go with them: `--source`, `--tests`, `--go-report`,
`--rust-report`, `--rust-lcov-report`.

**3. Add a coverage provider to any JavaScript component.** `vitest --coverage`
needs `@vitest/coverage-v8` (or `@vitest/coverage-istanbul`) in the workspace's
own dependencies. lydite does not add it: installing a dependency into the
repository it is about to gate would have lydite change what that repository
resolves to. Without it the component fails with
`Cannot find dependency '@vitest/coverage-v8'`.

**4. You no longer need a run on the default branch.** Baselines are keyed by
tree, and a squash merge lands the tree the pull request already measured — so
the number a change measures is the baseline for the commit it becomes. A
workflow that ran `lydite coverage` on pushes to `main` purely to record
baselines can stop.

**5. Every repository takes one cache miss.** Baselines move to `v3/` on the
`lydite` branch because they are a different quantity: per-component covered
and total line counts rather than per-language percentages. The first change
after upgrading reports every component as having no baseline yet, measures the
base tree once, and gates normally from then on. Older entries are left in
place and never read again.

## What the numbers mean now

**Three figures, all gated: per component, per language, and globally.** All
three are `Σ covered / Σ total` over subsets of the same stored per-component
counts, so they cannot disagree.

**Go coverage will move, upwards, and it is the correct number.** The
instrumented Go run now carries `-coverpkg=./...`. Without it Go instruments
only the package under test, so code exercised solely through another package's
tests read as uncovered — layered code penalised exactly in proportion to how
well it is layered. Measured on a two-package fixture where `b` is exercised
only through `a`'s test, the total goes from 25.0% to 100.0%.

**`coverage.floor` now gates the component, not the crate or package.** This is
a change in what is measured rather than a weakening: an untested crate inside
a workspace still contributes its lines as uncovered and still drags its
component's figure down in proportion to its size. What a component-level floor
cannot catch is a *small* untested sub-unit — one too small to move its
component's figure. A repository that wants crate-level floors declares those
crates as components.

**Patch coverage gates per component**, against that component's own baseline
rather than a language-wide one. A change to a well-tested component held to the
repository's average is held to nothing; one to a poorly tested component is
failed for reaching the standard it already has.

**A run that measured but did not gate renders distinctly from a pass.** The
coverage rows are context rows (`→`), never `✓`, and `--json` carries the
status by name. A workflow that forgets `--gate-coverage` reports no green it
did not earn.

## Also in this release

**`--base-branch`, and the default branch is discovered.** Every gate that
measures a change against "before it" — the coverage baseline, `--affected`,
`scan --diff-base auto`, `review --base auto` — resolved `origin/main` and
nothing else, so a repository whose default branch is `master` could run none of
them. The branch now comes from `--base-branch`, else `origin/HEAD`, else
whichever of `main` and `master` the remote has; a repository carrying both is
an error rather than a guess. The remote is still `origin`.

**`cargo-llvm-cov` is pinned and installed**, like every other tool lydite runs.
It was assumed on `PATH`, so a runner without it measured nothing — and an empty
baseline, once cached, makes every later change a cache hit that gates on
nothing.

**A component rooted at `.` no longer suppresses affected selection's
widening.** `dir: .` says where a component is rooted, not that it tests every
file in the tree, and reading its containment as a match switched the widening
rule off for the whole repository. In a repository with components at `.` and
`web/`, expect nearly every change to select everything: the optimisation
largely stops applying there, which is the safe direction and is visible in the
`select` row.

## One thing to know before wiring it into CI

`--gate-coverage` records the baseline, which is a push to the `lydite` branch — so the job needs
`contents: write`. That same job runs your test suite, and on a pull request that is the pull
request's own code. A writable token in a job that runs a branch's code is write access to the
repository for anyone who can open a pull request from a branch.

Running the gate with a **read-only** token is supported and is what lydite's own CI does: the write
fails, the report says `not recorded`, and the verdict is unaffected. What you lose is the cache, so
every run measures the base tree instead of reading a recorded one — one extra instrumented run per
change. Separating measuring from recording is tracked in
[#49](https://github.com/lydite/lydite/issues/49).

## `lydite/actions`

The action still invokes `lydite coverage` and must be cut over to `lydite test
--gate-coverage`. That is a change in `lydite/actions`, released separately.
