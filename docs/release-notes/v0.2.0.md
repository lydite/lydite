# v0.2.0 — the component is the unit, for coverage and for scanning

`lydite coverage` is removed. `lydite test` measures every component's coverage
from the instrumented variant its runner already derives, and
`lydite test --gate-coverage` gates it against the baseline.

`lydite scan` reads the same declaration. It no longer walks the tree for
`Cargo.toml`, `package.json` and `go.mod`: a component names a runner, the
runner implies a language, and its `dir` is where that language's checks run.

This is the release where the component — declared in `.lydite/components.yml`,
introduced across the previous releases — becomes the unit lydite measures,
gates **and scans**. Both were the last things still discovering their own units
by walking for manifests.

## Upgrading

**1. Replace the command.**

```sh
lydite coverage --dir .                     # before
lydite test --dir . --gate-coverage         # now
```

`lydite test` measures coverage on every run; `--gate-coverage` is what reads
the baseline and compares against it. The flag is explicit because measuring is
local and reading a baseline touches the network — a developer's `lydite test`
should not need a remote. `--no-coverage` runs each component's plain variant
and reports no coverage at all.

Recording is a second command — see *Measuring and recording are two commands*
below.

Running `lydite coverage` now fails with a message naming its replacement
rather than "unknown command".

**2. Remove these keys from `.lydite/config.yml`.** Each is now **rejected**,
not ignored — a silently dropped key is a repository measuring something other
than what its author wrote while every run still reports a pass.

| Removed | Why |
|---|---|
| `coverage.source` | lydite measures from each component's own instrumented run, so no pipeline half owns producing coverage |
| `coverage.go.report` | lydite writes every report itself, at a path derived from the component's runner |
| `coverage.rust.report` | as above |
| `coverage.rust.lcov` | as above |

The matching flags go with them: `--source`, `--tests`, `--go-report`,
`--rust-report`, `--rust-lcov-report`.

**3. Declare your components, or `lydite scan` will refuse to run.** With
nothing in `.lydite/components.yml` there is nothing for scan to scan, and it
exits 1 naming the file rather than reporting a repository nobody scanned as
clean:

```
lydite: no components declared in .lydite/components.yml: scan runs the checks
each component's language implies, so declare what this repository builds
```

If you already run `lydite test`, you already have this file and there is
nothing to do. If you ran only `lydite scan`, this is the one upgrade step that
is real work — and it is the same declaration `lydite test` needs, so it is not
work spent only on this.

Two consequences worth expecting. A Cargo workspace is now scanned **once**, at
the component root, rather than once per member crate detection resolved; a
JavaScript workspace is linted once rather than once per nested `package.json`.
Findings do not change — both tools already walked from there — but the row
count does, and rows are now labelled by component name (`gosec(cli)`,
`cargo clippy(api)`).

Source that no component's checks reach is named on stderr rather than passing
in silence: `warning: N go file(s) are under no component that checks them`.
Declare a component for it, or add it to `excludes` in `.lydite/components.yml`
— which is the reviewable statement that this code is scanned by nobody and
somebody decided that.

**4. Remove these keys too.** They narrowed the detection walk, and there is no
walk left to narrow. Rejected by name, like the coverage keys above.

| Removed | Why |
|---|---|
| `rust.exclude` | lydite scans what `.lydite/components.yml` declares; a directory no component declares is already out of scope |
| `typescript.exclude` | as above |
| `go.exclude` | as above |

A directory that exists only to hold a pinned manifest needs no exclude now:
nothing declares it, so nothing scans it. A subdirectory *inside* a component
that should not be linted is that language's own tool configuration to state
(`biome.json`, `clippy.toml`).

**5. Add a coverage provider to any JavaScript component.** `vitest --coverage`
needs `@vitest/coverage-v8` (or `@vitest/coverage-istanbul`) in the workspace's
own dependencies. lydite does not add it: installing a dependency into the
repository it is about to gate would have lydite change what that repository
resolves to. Without it the component fails with
`Cannot find dependency '@vitest/coverage-v8'`.

**6. Add a recording step, or stop recording.** `--gate-coverage` no longer
writes anything. If you want the cache, run `lydite test record` in a job that
holds `contents: write` — and read the next section before deciding which job
that is. Without it every run is a cache miss: correct, slower, and the
`record` row says so.

**7. Every repository takes one cache miss.** Baselines move to `v4/` on the
`lydite` branch because they are a different quantity: per-component covered and
total line counts with the instrument that measured them, rather than
per-language percentages. The first change after upgrading reports every
component as having no baseline yet, measures the base tree once, and gates
normally from then on. Older entries are left in place and never read again.

## What the numbers mean now

**Two figures, both gated: per component, and over the repository.** Both are
`Σ covered / Σ total` over subsets of the same stored per-component counts, so
they cannot disagree. A language is not an altitude — it is a grouping derived
from each component's runner rather than a unit anybody declared.

**Go coverage will move, upwards, and it is the correct number.** The
instrumented Go run now carries `-coverpkg=./...`. Without it Go instruments
only the package under test, so code exercised solely through another package's
tests read as uncovered — layered code penalised exactly in proportion to how
well it is layered. Measured on a two-package fixture where `b` is exercised
only through `a`'s test, the total goes from 25.0% to 100.0%.

**`coverage.floor` now gates the component, not the crate or package.** This is
a change in what is measured rather than a weakening: an untested crate inside
a workspace still contributes its lines as uncovered and still drags its
component's figure down in proportion to its size. What a component-level floor
cannot catch is a *small* untested sub-unit — one too small to move its
component's figure. A repository that wants crate-level floors declares those
crates as components.

**Patch coverage gates per component**, against that component's own baseline
rather than a language-wide one. A change to a well-tested component held to the
repository's average is held to nothing; one to a poorly tested component is
failed for reaching the standard it already has.

**A run that measured but did not gate renders distinctly from a pass.** The
coverage rows are context rows (`→`), never `✓`, and `--json` carries the
status by name. A workflow that forgets `--gate-coverage` reports no green it
did not earn.

## Also in this release

**A toolchain is resolved per component.** `engines.node` was read from every
detected package with the highest floor winning, so a workspace needing Node 22
and a tools package pinning 18 got one runtime chosen by a rule neither of them
stated. Each component now resolves against its own directory — its `go.mod`,
its `rust-toolchain.toml`, its `engines.node` then its `.nvmrc` then the scan
root's — and components asking for the same thing share one install. The
environment is handed to each component's own commands rather than written into
lydite's process, which is what lets two of them differ.

**`--base-branch`, and the default branch is discovered.** Every gate that
measures a change against "before it" — the coverage baseline, `--affected`,
`scan --diff-base auto`, `review --base auto` — resolved `origin/main` and
nothing else, so a repository whose default branch is `master` could run none of
them. The branch now comes from `--base-branch`, else `origin/HEAD`, else
whichever of `main` and `master` the remote has; a repository carrying both is
an error rather than a guess. The remote is still `origin`.

**`cargo-llvm-cov` is pinned and installed**, like every other tool lydite runs.
It was assumed on `PATH`, so a runner without it measured nothing — and an empty
baseline, once cached, makes every later change a cache hit that gates on
nothing.

**A component rooted at `.` no longer suppresses affected selection's
widening.** `dir: .` says where a component is rooted, not that it tests every
file in the tree, and reading its containment as a match switched the widening
rule off for the whole repository. In a repository with components at `.` and
`web/`, expect nearly every change to select everything: the optimisation
largely stops applying there, which is the safe direction and is visible in the
`select` row.

## Measuring and recording are two commands

Recording the baseline is a push to the `lydite` branch. Measuring runs your test
suite and any `setup`/`teardown` shell your components declare, and on a pull
request that is the pull request's own code. One command doing both puts a token
that can push into a job that runs arbitrary code.

So `lydite test` now writes nothing to that branch. It leaves what it would
record in `.lydite-reports/baseline.json`, and a second command lands it:

```sh
lydite test record --dir . --reports .lydite-reports
```

It runs nothing from your repository — no suite, no `setup` or `teardown`
command, no compose service — and it refuses a candidate whose tree is not the
one checked out. `--reports` is repeatable, so a sharded run folds into one
recording.

**Put it after the merge, not on the pull request.** The split takes the token
out of the job running your code; it does not make a branch's numbers
trustworthy, because a command that executes nothing verifies nothing. lydite's
own CI gates read-only on pull requests and records on pushes to the default
branch — see `.github/workflows/lydite-baseline.yml`, which is meant to be
copied. Keying by tree is what makes that cheap: the tree a squash merge lands
is the tree the pull request already measured, so the entry recorded after the
merge is the baseline the next pull request reads.

[#49](https://github.com/lydite/lydite/issues/49) has the full argument, and
[ADR 0025](../adr/0025-a-baseline-records-its-producer-and-only-record-writes-it.md)
records what this does and does not close.

## A baseline now records what measured it

A coverage figure is comparable only to one the same instrument produced. Bumping
vitest 3.2.7 → 4.1.11 over an identical tree took one workspace from 345
coverable lines to 152 — 185 of the 193 lines that stopped being counted were
covered ones — and the gate called it a regression by the author of the bump.

Each entry now records its producer: the Go toolchain, `cargo-llvm-cov` with the
Rust toolchain, or a JavaScript workspace's own runner and coverage provider read
back from `node_modules`. A component whose recorded producer differs from this
run's is reported **new** rather than **regressed**.

Expect one ungated change per bump of any of those, including a Go patch release
that changed nothing. That is the cost of never reporting a change of definition
as a regression, and it is visible in the row.

## `lydite/actions`

`lydite/actions` v1.1.0 already runs `lydite test --gate-coverage`. It needs the
recording step above before this release reaches consumers through it, or their
baselines silently stop being written — every run correct, and every run paying a
base-tree measurement.
