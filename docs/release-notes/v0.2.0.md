# v0.2.0 — the component is the unit, and a finding is a located claim

Every language-specific check lydite runs — coverage, CRAP, mutation, scanning,
linting — runs over a component declared in `.lydite/components.yml`; secrets
scanning and the repository-level coverage total are the exceptions, run once
over the whole tree. Everything a check has to say about a line is a finding
with a fingerprint and an anchor, rendered from the same claim wherever it
surfaces — a row in the terminal, an entry in `scan.json`, and, on a pull
request, either a section of the standing comment or a review thread on the
line it is about, never both.

What follows is what a consumer gets, what adopting costs, and which numbers
mean something different from what they meant in v0.1.0. The changelog below
lists what landed.

## Adopting this release

**1. Declare your components.** `.lydite/components.yml` is the declaration
`lydite test`, `lydite scan`, `lydite mutation` and `lydite review` all read, and
a repository that declares nothing is refused rather than reported clean:

```
no components declared in .lydite/components.yml: scan runs the checks each
component's language implies, so declare what this repository builds
```

A component names a `dir` and a `runner`; the runner implies the language, and
the language decides which checks run over that directory. Nothing walks the tree
for `Cargo.toml`, `package.json` or `go.mod`. Source no component reaches is
named on stderr — `warning: N go file(s) are under no component that checks them`
— and the answer is a component for it or an entry in `excludes`, which is the
reviewable statement that this code is scanned by nobody and somebody decided
that.

Two consequences worth expecting. A Cargo workspace is scanned **once**, at the
component root, and a JavaScript workspace is linted once rather than once per
nested `package.json`; the findings are the same, the row count is not, and rows
carry the component's name (`gosec(cli)`, `cargo clippy(api)`).

**2. State a licence policy, or the licence gate gates nothing.** `licence.policy.allow`
in `.lydite/config.yml` is a list of SPDX identifiers:

```yaml
licence:
  policy:
    allow: [Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, MIT, Unicode-3.0]
```

With no policy the row renders `not configured — state licence.policy.allow in
.lydite/config.yml` and decides nothing — a gate that could not run never renders
as one that passed. A Rust component with its own `deny.toml` and no lydite policy
is the one exception: cargo-deny's document gates it absolutely, because
grandfathering a check somebody opted into deliberately would weaken it.

**3. Move to the matching `lydite/actions@v1`.** The CLI release and the action
tag are a pair: `@v1` moves to the release whose actions invoke this CLI's
commands, and it cannot move ahead of the CLI they call. Consumers pinning `@v1`
get both at once; a consumer pinning a patch tag moves it themselves.

**4. Expect every pull request to be referred.** `lydite review` is an allowlist
whose default is to refer, and with no `.lydite/exemptions.yml` — or an empty one
— every change is referred, including a correct one. That is the day-one state,
and for most changes it is the state to keep. There is no built-in exemption for a
dependency bump: whether a lockfile-only bump can merge unattended is open design
([#23](https://github.com/lydite/lydite/issues/23),
[#82](https://github.com/lydite/lydite/issues/82)), so a Dependabot pull request is
referred like any other until a repository writes an exemption for it. An edit to
`.github/workflows/` or to anything under `.lydite/` is a built-in disqualifier
that no exemption can clear, so a workflow bump stays referred whatever is
declared.

**5. Drop the keys lydite rejects.** Each is refused by name, not
ignored — a silently dropped key is a repository measuring something other than
what its author wrote while every run reports a pass.

| Removed | Why |
|---|---|
| `coverage.source` | lydite measures from each component's own instrumented run, so no pipeline half owns producing coverage |
| `coverage.go.report`, `coverage.rust.report`, `coverage.rust.lcov` | lydite writes every report itself, at a path derived from the component's runner |
| `rust.exclude`, `typescript.exclude`, `go.exclude` | there is no detection walk to narrow; a directory no component declares is already out of scope |

The matching flags go with them: `--source`, `--tests`, `--go-report`,
`--rust-report`, `--rust-lcov-report`.

**6. Give a JavaScript component a coverage provider.** `vitest --coverage` needs
`@vitest/coverage-v8` (or `@vitest/coverage-istanbul`) in the workspace's own
dependencies. lydite does not add it: installing a dependency into the repository
it is about to gate would have lydite change what that repository resolves to.
That install runs at the **workspace root** — the nearest ancestor of the
component's `dir` holding a recognised lockfile — not in the component's own
directory, so a component nested under a monorepo's root installs from where its
dependencies actually resolve. Every component resolving the same root shares
one frozen install: the first to reach it runs `npm ci`, `yarn install
--immutable` or `pnpm install --frozen-lockfile` once, and the coverage or
mutation producer is read from wherever that install wrote `node_modules`, so a
nested component whose dependencies hoist above it no longer reports no
producer at all. A raw `command:` component joins the same install when its own
directory holds a `package.json`, rather than letting the package manager
auto-install the workspace on its own schedule and race lydite's. Two
components resolving one root must declare the same `env:`; declaring different
ones is refused, because the install runs once, under whichever declaration
reached it first. A component under no resolvable root — no single lockfile
between its `dir` and the scan root — gets its own `install(<name>)` row
instead of failing the suite, which still runs, with the value `not installed`:
`unmeasured`, not a pass or a fail, because the suite still ran and the row
claims only that lydite did not put the dependencies there.

**7. Record the baseline in a job of its own.** `lydite test` writes nothing to the
`lydite` branch. It leaves what it would record in `.lydite-reports/`, and
`lydite test record --reports .lydite-reports` lands it — a command that runs no
suite, no `setup` or `teardown`, and no compose service, and that refuses a
candidate whose tree is not the one checked out. Put it after the merge, not on the
pull request: the split takes a token that can push out of the job running the
branch's code, and keying by tree makes it cheap, because the tree a squash merge
lands is the tree the pull request already measured.
`.github/workflows/lydite-baseline.yml` is that workflow, and is meant to be
copied.

## What the numbers mean now

**`lydite coverage` is gone.** `lydite test` measures every component's coverage
from the instrumented variant its runner derives, on every run, and
`--gate-coverage` is what reads the baseline and compares against it. The flag is
explicit because measuring is local and reading a baseline touches the network — a
developer's `lydite test` should not need a remote — and `--no-coverage` runs each
component's plain variant and reports no coverage at all. Running `lydite coverage`
fails with a message naming its replacement rather than "unknown command". A run
that measured without gating renders as context rows (`→`), never `✓`, so a workflow
that forgot the flag reports no green it did not earn.

**Coverage gates the component and the repository**, both as `Σ covered / Σ total`
over the same stored per-component counts, so they cannot disagree. `coverage.floor`
holds the component; patch coverage gates a change against that component's own
baseline rather than a language-wide average. A repository that wants crate-level
floors declares those crates as components. The instrumented Go run carries
`-coverpkg=./...`, so code exercised only through another package's tests counts as
covered — on a two-package fixture where `b` is exercised only through `a`'s test,
the total is 100.0% rather than 25.0%.

**A baseline entry records its producer, and a producer change reads as `new`.**
A coverage figure is comparable only to one the same instrument produced: bumping
vitest 3.2.7 → 4.1.11 over an identical tree took one workspace from 345 coverable
lines to 152, and a gate without producers calls that a regression by the author of
the bump. Each entry carries the Go toolchain, `cargo-llvm-cov` with the Rust
toolchain, or a JavaScript workspace's own runner and coverage provider, and a
component whose recorded producer differs from this run's is reported **new**
rather than **regressed**.

That string names the toolchain provisioning actually installed, re-probed under the
environment provisioning produced, rather than the manifest's raw declaration
(`stable`, `1.26`). A repository whose baselines were recorded on a provisioned runner
therefore sees one producer change per affected component — one `new` reading each, and
one govulncheck tool-cache miss — and gates normally from then on.

**Baselines live under `v4/` on the `lydite` branch**, because they are a different
quantity from v0.1.0's per-language percentages: per-component covered and total line
counts with the instrument that measured them. The first change after upgrading
measures the base tree once. Older entries are left in place and never read again.

## Scanning

**Secrets.** A pinned gitleaks runs once over the scan root's working tree, never
over history. gitleaks itself walks every file under that root, so its claims are
filtered back to the files git would carry out of it: a leak in a path git ignores
— a warm `target/`, an installed `node_modules/` — produces no claim, while a file
that is merely untracked but not ignored stays in scope, since it is one `git add .`
away from being published. That is a scoping and not a suppression, and the cost is
stated openly: a real credential sitting in an ignored file is not reported. Its
claims name no component, because the files most likely to carry a credential — a
workflow, a `docker-compose.yml`, an `.env` — belong to none. The gate never quotes
the secret, in the terminal or in `scan.json` or in a finding's site, and every
message it writes says to rotate the credential, because deleting one does not undo
the leak. `secrets.enabled` in `.lydite/config.yml` turns it off; a false positive is
answered in gitleaks' own configuration.

**Licences.** Go, Rust and TypeScript dependency licences are checked against
`licence.policy.allow`. The gate is the set of non-conforming `(package, licence)`
pairs a change *introduces*: a pair present at the merge-base is grandfathered, so
adopting the policy never fails a repository over what it already ships. Go classifies
over `go list -deps`; Rust reads cargo-deny's own rejections under a policy generated
from the allow-list; TypeScript reads npm's `package-lock.json` directly, and `scan`
never runs an install to answer the question — a yarn or pnpm component without an
already-installed tree answers `unmeasured`, naming why. That lockfile is read at
the **workspace root** the component's own directory resolves — a member of a
workspace declares its dependencies nowhere, so reading the component's own
directory alone would answer a nested one `unmeasured` for a lockfile that exists
one directory up — and the set it produces is scoped back to that one component's
own closure, using the importer structure npm's lockfile records, rather than to
the whole root. A nested yarn or pnpm member has no such structure to scope by:
neither manager's lockfile records which dependency belongs to which workspace
member, and reading the installed tree at the root whole would report every
sibling's dependencies as this component's, so a nested member under those two
answers `unmeasured` instead.

**Rust's own tools run once per component.** clippy, cargo-audit and cargo-deny run at
the component root — each already walks the workspace from there — and lydite renders
their findings as its own rows and claims.

**Every scanner reports findings as data**, not only as a row: gosec, govulncheck,
Semgrep, gitleaks, clippy, cargo-audit, cargo-deny, Biome and the licence gate each
write located claims into `scan.json`. A component declaring a raw `command:`
implies no language and therefore none of these, and it is not left off the
report: it gets one row per gate a scanned component gets instead, each naming
why in its own words —

```
scan(<name>)     not scanned — the component declares a raw command, which implies no
                 language, so no linter, vulnerability or SAST check runs over it
licence(<name>)  not measured — the component declares a raw command, which implies no
                 language, so there is no dependency set to read licences from
findings(<name>) not counted — the component declares a raw command, which implies no
                 language, so no gate reports a finding count for it
```

— every one of them `unmeasured` rather than a failure, because the verdict stays
`pass`: declaring a raw command is a configuration the repository is entitled to
make, and what must not happen is silence about it.

**A `.semgrepignore` at the scan root is named on stderr**, because it replaces
Semgrep's defaults rather than extending them, and a scan that silently stopped
looking at a directory is worth one line.

**A component's declared `env:` is named back**, per component, before its checks run.
Nothing is refused and the declaration stays the repository's own — a declared
`GOFLAGS` still changes what gosec compiles, and the answer to that is to say so out
loud rather than to filter a list that would have to be complete to be safe.

## Gates

**CRAP scores Go, Rust and TypeScript.** Complexity comes from `go/ast` in Go and from
tree-sitter in Rust, TypeScript and TSX, so the gate on functions above the threshold
holds in all three rather than in Go alone. Under `--gate-coverage` it gates the delta
above the threshold against the baseline, and a failing row makes one claim per function.

**The flaky gate covers three languages.** `lydite test --gate-flaky` reruns every test
a change introduces, once, in a process of its own — `go test`, cargo-nextest and vitest
— and fails on a test whose two outcomes disagree. "New" is a test the merge-base's tree
does not declare and HEAD's does, read from the syntax rather than from the diff's lines.
jest is a named gap.

**Mutation is bounded in memory as well as in time.** A mutant whose suite allocates
without end is as unkillable as one that hangs, and both count as killed rather than
taking the machine down. Both bounds derive from the component's own baseline run;
`--timeout` and `--memory` state them explicitly. A run that asked for a memory bound and
did not get one says so rather than passing quietly.

**An undeclared Go public API break fails; a declared one is referred.** A component opts
in with `api_surface`, and the exported API of its Go module is compared against the
merge-base. The author clears an undeclared break by not breaking the API or by declaring
it; a declared break reaches a person, and so does a declaration with no detected break.
The surface diff is evidence read off two trees, and the declaration is a claim read off
the author's own text — an author-controlled claim may add a referral, never remove one.

**A tag whose range declares a break must be the bump that allows it.** `lydite release
check` reads every commit the tag closes and fails the release before goreleaser runs if a
declared break lands on a number that does not admit one. It is a failure rather than a
warning because nothing pins lydite's version for a consumer, so the bump number is the
entire warning anybody gets.

## The pull-request surface

**One standing comment, rendered by the CLI.** `lydite publish --reports <dir>` takes one
or more report directories and writes the comment; it opens no network connection and knows
no hosting platform, so a developer reads locally exactly what a reviewer sees, and a
sharded run is more directories and nothing else. Every command writes its document into
`.lydite-reports/` on every run, not only under `--json`.

**A located finding becomes a review thread.** `lydite threads` reconciles the threads on a
pull request with the run's findings, opening, answering and closing them from the
fingerprint and anchor each claim carries, so a finding that moved with an edit is the same
thread rather than a new one.

**Comments and threads post under lydite's own GitHub App**, through the OIDC relay, so the
surface arrives as `lydite` rather than as the consumer's `github-actions[bot]`. The App
stays optional: a repository that has not installed it falls back to `github-token` silently.
A relay answer on `/comment` that is deterministically wrong — a mistyped audience, a version
the relay will not apply — **fails the step** instead of falling back, because retrying it
answers the same and a silent fallback there hides a misconfiguration forever. `/review`'s
`403` is the exception and falls back under a warning, because it is ambiguous with a
comment-id race. The `lydite/referral` commit status is not part of this: it is published by
the job's own token. The relay's `/status` route is written and tested but the deployed Worker
predates it, so no status goes through the relay for anyone; and `REFERRAL_WORKFLOW_REFS` and
`CLEARANCE_WORKFLOW_REFS`, the two allowlist vars on lydite's own relay, both ship empty and
admit no job.
`.github/workflows/lydite-pr.yml`'s `referral-publish` job holds `statuses: write` and posts
the status directly.

**A concern the repository declined renders as declined.** `lydite mutation --declined` writes
its report and the section says so, rather than disappearing — a section that quietly vanishes
is indistinguishable from a concern that passed. A missing input is likewise a section saying
what was missing, never an omission.

## Answering a referral by comment

**A referral is resolved by a person commenting, never by pushing more code.** A comment whose
first line addresses lydite is the surface — only the first line, so a reply quoting an earlier
comment clears nothing — and it has three verbs. `/lydite clear` resolves the referral standing
on the pull request's current head, from a commenter the platform says has push permission.
`/lydite explain` restates the standing verdict and changes nothing. `/lydite exempt <shape>`
drafts an exemptions-file entry. Anything else is refused by name:

```
unknown command — this surface has `/lydite clear`, `/lydite explain` and `/lydite exempt
<shape>`, where a shape is up to 64 letters, digits, dots, dashes and underscores
```

A clearance names one revision, so any push produces a new head carrying no verdict and the
clearance does not travel with the branch.

**`/lydite exempt <shape>` proposes an entry and lands nothing.** It is a comment verb, not a
subcommand, and its one argument is the `name` the entry will carry. It takes no glob: a pattern
the commenter typed would widen the proposal past what their own change needs covered, and a
block that reads as lydite's output is the one a reviewer is least likely to re-derive. `paths`
is the change's own uncovered set — the paths no declared exemption covers — glob-escaped,
because a `paths:` entry is a pattern and a filename is not, so `app/[slug]/page.tsx` proposes a
literal match rather than a character class covering `app/s/page.tsx` and missing its own file.
A rename contributes both of its names.

**What it produces cannot be merged unedited, by design.** The verb posts a new comment holding
a paste-ready YAML block. It never edits the standing comment, writes no status and makes no
commit, and the referral stands until a human merges an entry into `.lydite/exemptions.yml` on
the default branch. The `reason` is a question rather than a sentence:

```yaml
exemptions:
  - name: docs-only
    reason: "TODO(lydite): why is a change touching only these paths safe to merge unread?
      State what this entry's paths guarantee, and nothing the schema does not check."
    paths:
      - docs/release-notes/v0.2.0.md
```

`TODO(lydite):` is reserved, and the exemptions-file parser rejects any exemption whose reason
carries it anywhere:

```
reason still carries lydite's own placeholder marker — an exemption needs a person's
judgement, not a generated question
```

The check is in the parser rather than in the generator, so it holds however the block arrived —
copied by hand, pasted by an editor, or written from scratch. A templated real-sounding reason
was the alternative, and prose that already reads as though somebody thought about it is prose
that defeats the requirement that somebody did.

## Quality history

**The ledger appends what cannot be recomputed.** `lydite test record` writes per-month NDJSON
partitions under `history/v1/` on the `lydite` branch, alongside the baseline, in one commit.
Records are appended, never edited: the pins that produced a number may have moved, and after a
squash merge the commit it describes no longer exists. Every record names its commit's first
parent, and an explicit `gap` record states how many commits lie between it and the last one, so
a reader finds a break in the series using the file it is already reading. A commit whose suite
went red establishes no baseline and is recorded anyway — how many tests ran and how many failed
is exactly what a history wants.

**Each gate's finding count is recorded**, so the history carries how much each scanner said and
not only whether the row passed.

**Mutation scalars reach the ledger from a post-merge run.** A mutant exists only on a line a
change touched, and on the default branch HEAD is its own merge-base — so the recording job
mutates the merge commit's own first-parent diff, `--base-sha HEAD~1`, and folds those documents
into the same `record` call. The cost is accepted: mutation runs twice per change, once
read-only on the pull request where it gates, and once after the merge where it is recorded.

## Correctness for consumers

**A repository with one shard folds and records correctly.** `actions/download-artifact` gives an
artifact its own subdirectory only when the pattern matched more than one and extracts a lone
match flat, so a fold that globs directories walks into a shard's own log directory instead. Every
fold locates the document a shard must have written and folds whatever directories that returns.

**The toolchain lydite decides on is the one that runs.** A Rust component's satisfaction is asked
of `rustup` from the component's own directory rather than inferred from an ambient
`cargo --version`, so a component pinning an older channel, or missing clippy or rustfmt, is
provisioned rather than silently passed. Each component resolves against its own directory — its
`go.mod`, its `rust-toolchain.toml`, its `engines.node` then its `.nvmrc` then the scan root's —
and components asking for the same thing share one install. The environment is handed to each
component's commands rather than written into lydite's process, which is what lets two of them
differ.

**An exclusion declaration takes effect in Rust and TypeScript.**
`[lydite:exclude_from_<gate>][<reason>]` is scoped by a parser in every language — `go/ast` in Go,
tree-sitter elsewhere — rather than by the coverage report, which has line hits and no syntax tree.
A declaration covers the function whose doc comment holds it in all three languages, and the
suppression it costs the author buys what it says it buys.

**`--base-branch`, and the default branch is discovered.** Every gate that measures a change
against "before it" takes the branch from `--base-branch`, else `origin/HEAD`, else whichever of
`main` and `master` the remote has; a repository carrying both is an error rather than a guess. The
remote is still `origin`.

## What a component may declare

```yaml
components:
  - name: cli
    dir: source/cli
    runner: go-test
    args: ["-race", "./..."]
    env:
      CGO_ENABLED: "0"
    mutation: false        # opt out; the default is true
    api_surface: {}        # opt in; the default is unmeasured
  - name: docs
    dir: docs/design
    command: [make, check]  # no runner: implies no language
excludes:
  - "source/cli/internal/**/*-pin/**"
```

`mutation: false` is a component nobody mutates, rendered as a context row rather than as silence.
`api_surface: {}` opts a Go component into the public-API diff — presence alone is the opt-in,
and the shape is a map rather than a boolean. `env:` reaches the checks that scan a
component as well as the suite that tests it, and its variable names are reported back in the scan
it shaped. `command:` runs a component's own suite verbatim in place of a derived runner variant,
naming no `runner:` and therefore no language — nothing here scans, measures coverage or checks
licences for it, and it reports so rather than reporting nothing.
