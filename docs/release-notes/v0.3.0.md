# v0.3.0 — Python and shell join the languages lydite measures, and a clearance survives a rebase

Two languages lydite could see but not judge now carry real checks. Python is parsed, so its
complexity is scored, its exclusion annotations land, and its mutants are generated and run. Shell
is scanned by ShellCheck, which needs a component shape that did not exist: a unit with a language
and no suite, declared with the new `lang:` key.

The other half of this release is the merge queue. A clearance names one revision and deliberately
does not travel, which made a required `lydite/referral` and a merge queue mutually exclusive — the
queue replays the change onto a fresh base, and nobody can clear a commit that has no pull request.
A clearance now records the fingerprint of the *decision* it was given for, so a queue entry whose
referral reasons are unchanged carries that clearance forward instead of deadlocking.

## Adopting this release

**1. Upgrade before you declare `lang:`.** The key is new, and `.lydite/components.yml` is parsed
strictly — an older binary rejects a file that uses it rather than ignoring the key. If your
pipeline pins a lydite version, move the pin first; if it tracks the latest release, nothing to do.

**2. Python components are measured, not skipped.** A Python component's complexity is scored and
its `[lydite:exclude_from_<gate>]` annotations are honoured, and `lydite mutation` generates
mutants for it. Expect CRAP rows and mutation rows where you previously had `unmeasured`, and
expect the first mutation run to surface survivors that were always there.

**3. Shell is scanned only where you switch it on.** Declare the directory as a component with a
language and no suite:

```yaml
components:
  - name: scripts
    dir: scripts
    lang: shell
```

and enable the language:

```yaml
shell:
  enabled: true
```

`shell.enabled` is the one language check that defaults to **off**. ShellCheck fails on every
diagnostic it reports, style included, so defaulting it on would fail the build of every
repository that happens to contain a `.sh`. A `lang: shell` component in a repository that has not
switched it on renders `unmeasured` naming the key — never a silent pass.

`lang:` and `runner:` are mutually exclusive: a runner already implies the language, and a second
statement could only disagree with it. A component with no invocation also refuses every key that
configures a suite (`args`, `setup`, `compose`, `occupies`, `mutation`, and the rest), because each
would be a declaration nothing reads. `env:` stays allowed — it reaches the scan's checks.
`licence` stays `unmeasured` for shell and says why: shell declares no dependency set to read
licences from.

**4. Your package manager is provisioned; your `typescript.install` override probably is not
needed.** lydite reads `packageManager` from `package.json` and installs that exact pnpm or yarn
before running the install, so a runner with no pnpm on `PATH` no longer fails with
`exec: "pnpm": executable file not found in $PATH`. If you wrote a `typescript.install` override to
bootstrap a package manager, delete it.

If you kept an override to add a *step* — a browser download, a codegen pass — use `setup:` on the
component that needs it instead. `setup:` runs after the coalesced install, in that component's own
directory, with the provisioned toolchain on `PATH`:

```yaml
    setup:
      - npx playwright install --with-deps chromium
```

`typescript.install` still means "replace the whole install", but it no longer opts its component
out of install coalescing: where a workspace root resolves, the override now runs **once** at that
root under the same lock every detected install uses, instead of once per component against one
shared `node_modules`. Overrides that hand-rolled a mutex to work around that can drop it. The
report also renders a row for an overridden install now, naming the override and where it ran.

**5. A clearance carries a fingerprint, and that is not yet the whole merge-queue story.**
`/lydite clear` records the fingerprint of the decision it cleared — the uncovered paths and the
disqualifications, hashed as a set — and `lydite clearance queue` recomputes it against the queue's
own tree. Matching republishes `lydite/referral` as `success`, carrying the original clearer's
attribution forward; not matching publishes `pending` with a reason, so the entry leaves the queue
and a person clears it again. It never publishes `failure`, which is the isolation gate and would
make the entry permanently unclearable.

**The queue path is not live on this release alone.** It needs `lydite/actions` to wire its
`merge_group` trigger to `lydite clearance queue`, which ships separately. Until then, this
release changes nothing about a queue you already have.

One gap is deliberate and recorded in ADR 0057: a component whose API-surface comparison would run
the change's own build code fingerprints as *uncomputable* rather than being compared, because
computing it in the job that answers a `/lydite` comment would run a fork's build code in your
repository's context before any permission is checked. A clearance given for that kind of
disqualification goes back to a person at queue time instead of carrying forward.

**6. The quality history records which findings appeared and which were resolved.** The ledger held
only a count per gate; it now also records appearance and resolution transitions keyed by each
finding's fingerprint, so "when did this first appear?" is answerable. This is additive — no
`history/v1` bump, and a reader parses an older record as one with no finding events, which is what
it has.
