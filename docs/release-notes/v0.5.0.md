# v0.5.0 — `lydite test record` writes the open-findings snapshot beside the ledger record

The `lydite` branch's ledger carries a finding's detail as transitions: fingerprints that appeared
or resolved, never the set still open. Answering "what is open on this branch right now" meant
replaying the ledger, which holds fingerprints and no location, rule or message. `lydite test
record` now also writes that answer as a file, in the same commit as the ledger record. The
decision and what it rejected are in
[ADR 0081](../adr/0081-record-writes-the-open-findings-snapshot.md).

## The file

`snapshot/v1/<branch>/findings.json` on the `lydite` branch. A branch name's slashes are real
directories.

- **Parts.** When the document would pass 900 KiB it is split into `findings.json`,
  `findings.1.json`, `findings.2.json` and so on, so no part is over that size and each stays
  fetchable under the Contents API's 1 MiB cap.
- **Header.** Every part carries `{branch, commit, at, part, parts}`. Parts that disagree on
  `commit` or `parts`, or a part the header says exists and the branch lacks, are an incomplete
  set; a reader should treat it as absent rather than stitch it together.
- **Fields.** Each finding holds `gate`, `component`, `path`, `line`, `end_line`, `rule`,
  `severity`, `message`, `ordinal` and `fingerprint`. A field with no value is omitted.
- **No source excerpt.** `site`, the excerpt of source a finding sits on, and `detail`, the tool's
  extended text (gosec's is the quoted code, clippy's the rendered diagnostic), are not written.
  A secret a scanner flags would otherwise gain a second copy in the branch's history that nobody scrubs
  when the source is, and the branch is public for a public repository. Fetch the excerpt and extended text
  from the code at `path` and `line`.

## What is in it

Membership is the ledger's open set after this run's own events are applied, never the previous
snapshot's. For each open fingerprint:

- a gate and component this run measured takes its fields from this run's findings;
- one this run did not measure, because its scanner crashed or did not run, carries its fields
  forward from the previous snapshot where that holds the fingerprint;
- otherwise the entry is identity-only: `fingerprint`, `gate`, `component`.

A bucket whose scanner keeps crashing keeps its entries, but their fields go stale until a clean
run.

## When it is written

Only when the recording lands a record. A run for a SHA already recorded appends nothing and
writes no snapshot, because it would describe an open set the ledger has not moved to.

The snapshot is recomputable from the ledger plus a rerun. Losing it or tearing it costs fields,
never history, and the next recording rewrites it whole.

## What a consumer sees

- The `lydite test record` report gains an "open findings" row naming the parts written.
- The ledger record and the branch's existing files are unchanged.
